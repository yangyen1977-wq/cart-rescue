# CartRescue AI — 異常標示規範與價值展示

> **版本**: v1.0
> **日期**: 2026-09-17
> **負責**: Scout（斯考特）
> **受眾**: Vincent（老闆）與產品團隊
>
> **核心命題**: 異常的「標示方式」本身就是產品價值——客戶不只要知道「有問題」，更要清楚知道「這是什麼問題」「要不要修」「誰來修」。

---

## 一、為什麼「標示異常」是價值展示

### 1.1 競品如何標示異常

| 競品 | 異常呈現方式 | 問題 |
|------|------------|------|
| **Noibu** | 「JavaScript Error: undefined is not a function」| 工程師才看得懂，營運團隊無法行動 |
| **Datadog** | 「Browser Test Failed: Step 3 timeout」| 技術導向，沒有業務語意 |
| **Checkly** | 「Assertion failed: expect(page).toHaveTitle()」| 程式碼語言，非電商語言 |
| **Contentsquare** | 「Conversion rate dropped 12%」| 事後分析，無法即時預防 |

### 1.2 CartRescue 的差異化標示

**我們不說「測試失敗」，我們說：**

> 🚨 **「SUMMER20 折扣碼在結帳頁失效，預估每日影響營收 NT$12,500」**

**我們不說「Timeout error」，我們說：**

> ⚠️ **「付款頁面載入超過 30 秒，顧客可能在此流失」**

**我們不說「Element not found」，我們說：**

> 🔍 **「結帳頁的『應用折扣』按鈕消失，建議檢查前台上版紀錄」**

## 二、異常分類架構（10 大類型）

### 2.1 分類原則

根據 46 篇 arXiv 論文研究，特別是 **WebTestPilot (2602.11724)** 的「符號化 GUI 元素」方法論與 **HxAgent (2608.15491)** 的「每步狀態評估器」，我們將異常分為三大維度：

```
異常分類 = 嚴重度 × 可修復性 × 業務影響
```

### 2.2 十大異常類型

| # | 類型代碼 | 名稱 | 圖示 | 嚴重度 | 可修復性 | 典型影響 |
|---|---------|------|------|--------|---------|---------|
| 1 | `DISCOUNT_FAIL` | 折扣碼失效 | 🎫 | 🔴 Critical | 高（商家後台調整）| 直接營收損失 |
| 2 | `CHECKOUT_ERROR` | 結帳流程中斷 | 💳 | 🔴 Critical | 中（需工程師排查）| 購物車放棄率飆升 |
| 3 | `PAYMENT_TIMEOUT` | 支付頁面超時 | ⏱️ | 🔴 Critical | 中（支付商或網站）| 最後一步流失 |
| 4 | `PRICE_MISMATCH` | 價格不一致 | 💰 | 🔴 Critical | 高（後台設定錯誤）| 客訴與信任損失 |
| 5 | `PRODUCT_UNAVAILABLE` | 測試商品缺貨 | 📦 | 🟡 Warning | 高（補貨或換 SKU）| 無法完成審計 |
| 6 | `UI_REGRESSION` | 介面元素異常 | 🎨 | 🟡 Warning | 中（前端修正）| 用戶體驗下降 |
| 7 | `SHIPPING_ERROR` | 運送資訊錯誤 | 🚚 | 🟡 Warning | 中（物流設定）| 特定地區無法下單 |
| 8 | `LOGIN_REQUIRED` | 需登入才能結帳 | 🔐 | 🔵 Info | N/A（預期行為）| 非故障，需標示 |
| 9 | `CAPTCHA_BLOCKED` | 被驗證碼阻擋 | 🧩 | 🔵 Info | N/A（需人工介入）| 需加入白名單或調頻率 |
| 10 | `BOT_DETECTED` | 被防爬蟲系統攔截 | 🤖 | 🔵 Info | 中（IP 白名單）| 需與商家協調 |

### 2.3 異常嚴重度定義

| 等級 | 顏色 | 定義 | 回應時間 |
|------|------|------|---------|
| 🔴 **Critical** | 紅色 | 直接導致營收損失或客戶無法完成購買 | 立即（< 10 分鐘）|
| 🟡 **Warning** | 黃色 | 可能影響轉換率或特定用戶群體 | 當日（< 4 小時）|
| 🔵 **Info** | 藍色 | 非故障，但需記錄與追蹤 | 每週彙整報告 |
| ⚪ **Expected** | 灰色 | 預期行為（如測試訂單未付款）| 不需回應 |

## 四、非故障類型的標示價值（Info 級別）

### 4.1 為什麼要標示「非故障」？

**競品只報「失敗」，我們報「狀態」。**

這是基於 **HxAgent (2608.15491)** 的「狀態評估器」方法論——每一步都應清楚標示：
- ✅ 完成（Completed）
- ⚠️ 偏離（Deviation）
- 🚫 阻擋（Blocked）
- ℹ️ 預期限制（Expected Limitation）

### 4.2 Info 級別標示範例

#### 範例 1: Login Required（登入牆）

```
┌─────────────────────────────────────────────────┐
│ 🔵 Info  ·  LOGIN_REQUIRED                       │
│                                                 │
│ 該網站需登入會員才能進入結帳流程                    │
│                                                 │
│ 📍 發生位置: 購物車頁面（點擊「前往結帳」後）        │
│ 🕐 發現時間: 2026-09-17 08:35 CST                │
│                                                 │
│ ℹ️ 說明:                                         │
│    這是該網站的預期行為，非故障。                    │
│    商家設定了會員專屬結帳流程。                      │
│                                                 │
│ 💡 建議:                                         │
│    · 若商家希望測試完整結帳，可提供測試帳號         │
│    · 或調整審計範圍為「到購物車頁面」即可           │
│                                                 │
│ 📝 備註: CartRescue 無法也不應繞過登入機制         │
└─────────────────────────────────────────────────┘
```

**價值**: 客戶不會誤以為「CartRescue 壞了」或「我的網站壞了」。

│ 🕐 發現時間: 2026-09-17 08:35 CST                │
│                                                 │
│ ℹ️ 說明:                                         │
│    這是網站的安全機制，保護商家免受自動化攻擊。      │

│                                                 │
│ 💡 建議:                                         │
│    · 將 CartRescue 的 IP 加入白名單                │
│    · 或提供專用測試帳號（無 CAPTCHA）              │
│    · 或調整審計頻率（避免觸發風控）                 │

**價值**: 展示 CartRescue 的安全承諾，建立客戶信任。

## 五、異常標示的商業價值

### 5.1 對客戶的價值

| 標示特性 | 客戶獲得的價值 |
|---------|--------------|
| **電商語言** | 不用請工程師翻譯，營運團隊直接理解 |
| **影響量化** | 知道「不修會損失多少錢」，優先排序修復 |
| **修復指引** | 給出具體步驟，降低修復門檻 |
| **責任指派** | 清楚知道誰該處理（營運？工程師？支付商？）|
| **證據留存** | 截圖 + DOM，與工程師溝通時零誤差 |

### 5.2 對 CartRescue 的競爭優勢

```
競品報告: "Test failed: Step 3 timeout"
    ↓ 客戶的反應: ??? 什麼意思？要找誰？損失多少？

CartRescue 報告: "付款頁面載入超過 30 秒，預估每日損失 NT$8,000，
                  建議聯繫綠界科技（ECPay）檢查 API 回應時間"
    ↓ 客戶的反應: 清楚、可行動、有優先級
```

### 5.3 定價支撐

**「我們不賣『監控工具』，我們賣『營收保護服務』。」**

異常標示的精緻程度直接支撐定價：

| 方案 | 異常標示能力 | 月費 |
|------|------------|------|
| **Starter** | 基礎標示（類型 + 截圖）| NT$2,990 |
| **Growth** | 完整標示（+ 影響量化 + 修復建議）| NT$8,990 |
| **Enterprise** | 自定義標示（+ 自定義異常類型 + 多語言）| NT$26,900+ |

## 七、與論文研究的對應

### 7.1 技術基礎

| 論文 | 方法論 | CartRescue 標示應用 |
|------|--------|---------------------|
| **WebTestPilot (2602.11724)** | 符號化 GUI 斷言 | 每個異常都對應一個「符號」（Cart、Discount、Payment） |
| **HxAgent (2608.15491)** | 每步狀態評估器 | 每步都標示完成/偏離/阻擋，而非僅最終結果 |
| **AgentRewardBench (2504.08942)** | 判斷精確度評估 | 信心分數透明展示，讓客戶知道可信度 |
| **WASP (2504.18575)** | 安全分類 | 區分「故障」與「安全機制阻擋」 |
| **Open CaptchaWorld (2508.04266)** | CAPTCHA 處理 | 明確標示 CAPTCHA 為「預期限制」，非故障 |
| **WebMall (2508.13024)** | 結帳任務分解 | 10 步驟中哪一步失敗，精確定位 |

### 7.2 與競品的對比

| 能力 | Noibu | Datadog | CartRescue（我們）|
|------|-------|---------|------------------|
| 異常標示語言 | 技術導向 | 技術導向 | **電商業務導向** |
| 影響量化 | 回溯計算 | 無 | **即時預估** |
| 修復指引 | 無 | 無 | **步驟化建議** |
| 非故障標示 | 無 | 無 | **明確區分 Info 級別** |
| 信心透明度 | 無 | 無 | **分數 + 因子拆解** |

## 八、結論

### 核心論點

> **「異常的標示方式」是 CartRescue 的隱形護城河。**
>
> 競品告訴客戶「有問題」；
> CartRescue 告訴客戶「什麼問題、影響多少、怎麼修、誰來修」。
>
> 這不是 UI 設計的差異，是**產品哲學**的差異：
> ——我們不只是監控工具，我們是**營收保護夥伴**。
