## 測試焦點：Day 14 計畫落實

### 1. 計算隔離策略（Prompt 優化）

**背景**：Day 14 發現小模型在複雜促銷計算上「結構性理解缺陷」。Day 15 計畫嘗試「只提取資訊，不做計算」。

**測試設計**：
- Prompt 明確禁止計算：「你的任務只有一項：從產品頁面文字中提取所有價格相關資訊，**但不進行任何計算或判斷**」
- 輸出格式強制為 JSON，只包含原始資訊

**Qwen2.5:7b 結果**：

| 項目 | 結果 | 正確性 |
|------|------|--------|
| 產品名稱 | Classic Messenger Cordura® Eco 經典郵差包 S (14L) | ✅ |
| 定價提取 | NT$ 3680 | ✅ |
| 特價提取 | NT$ 3128, 3383, 2703 | ✅（主商品 3128 正確） |
| 促銷提取 | 約64折、約8折等 | ✅ |
| **計算行為** | **無任何計算** | ✅ **策略成功** |
| eval_count | 35 tokens | 極低 |

**結論**：計算隔離策略有效。Qwen 在嚴格指令下可只做資訊提取，不進行數學運算。這為「規則引擎 + 模型提取」組合架構奠定了基礎。

### 2. 多步驟導航測試（新場景：前置條件識別）

**背景**：TravelPlus 產品頁需要「先選顏色 → 再選尺寸 → 才能放入購物車」。這是一個比單純「點擊放入購物車」更複雜的決策場景。

**測試 Prompt**：
> 目前顏色尚未選擇。正確的下一步是什麼？
> A. 直接點擊「放入購物車」
> B. 先選擇一個顏色，再點擊「放入購物車」
> C. 點擊「立刻結帳」
> D. 點擊「前往結帳」

**結果**：

| 模型 | 答案 | eval_count | 推理 |
|------|------|-----------|------|
| **Qwen2.5:7b** | **B** ✅ | 35 | 「在選擇完顏色和尺寸後才能將商品加入購物車」 |
| **Gemma3:4b** | **B** ✅ | 41 | 「必須先選擇顏色和尺寸後才能點擊」 |
| **Llama3.2:3b** | **B** ✅ | 21 | （簡短正確） |

**結論**：
- **三模型全部正確**：即使在需要「理解前置條件」的多步驟場景，本地小模型仍能做出正確導航決策。
- **導航能力與計算能力是解耦的**：模型可以正確導航（理解流程）但無法正確計算（理解數學），這進一步支持「規則引擎 + 模型提取」的分工架構。
- **Llama eval_count 最低**（21），但答案簡短無推理，適合快速響應場景。

### 3. 規則引擎原型 v2（核心實驗）

**背景**：Day 14 計畫提出「設計促銷規則引擎——用正規表達式解析價格與促銷，不依賴模型推理」。Day 15 完成原型開發與測試。

#### 引擎架構

```
CartRescueRuleEngine
├── extract_prices(text)      → 正規表達式提取價格
├── extract_discounts(text)   → 正規表達式提取折扣標示
├── infer_list_price(...)     → 無定價時從折扣反推
├── calculate_expected(...)   → 純數學計算（無 LLM）
└── audit(text)               → 整合輸出 + 風險評級
```

#### 測試一：TravelPlus（簡單場景）

| 項目 | 結果 |
|------|------|
| 定價提取 | ✅ NT$ 3680 |
| 特價提取 | ✅ NT$ 3128 |
| 折扣計算 | ✅ 15.0%（=(3680-3128)/3680） |
| 等價折扣率 | ✅ 8.5折 |
| 風險評級 | ✅ **Low**（正常折扣範圍） |

**重要發現**：頁面標示「約64折」，但實際計算為「8.5折」。這是一個**頁面標示錯誤或誤導**！
- 如果「64折」意指「6.4折」（即 36% off），則售價應為 3680 × 0.64 = **NT$ 2,355**
- 實際售價 NT$ 3,128 對應 **8.5折**（15% off）
- **結論**：「約64折」標示可能是錯誤的，或指的是其他意義（如品牌折扣而非此商品）

#### 測試二：momo（複雜場景 — 無定價）

| 項目 | 結果 |
|------|------|
| 促銷價提取 | ✅ $4,100 |
| 折後價提取 | ✅ $3,390 |
| 定價提取 | ❌ 無直接定價 |
| **反推定價** | ✅ **$4,556**（從「9折」+ 促銷價 $4,100 反推：4100 / 0.9 ≈ 4556） |
| 折扣一致性 | ✅ 反推定價與「9折」標示一致 |
| 風險評級 | ✅ **Low**（10% 折扣，正常範圍） |

**關鍵突破**：
- **無定價時可從折扣標示反推**：當頁面只有「折後價」而無「定價」時，規則引擎可利用「9折」標示反推原始定價。
- **這解決了 momo 的核心問題**：Day 14 中三個 LLM 都無法正確推斷原價，但規則引擎可以。

## 發現的問題或驚喜

### 🎉 重大驚喜

1. **規則引擎 v2 成功替代 LLM 數學推理**：
   - TravelPlus：正確計算 15% 折扣，評級 Low
   - momo：無定價時從「9折」反推 $4,556，與頁面標示一致
   - **零 LLM 參與計算，100% 確定性輸出**

2. **計算隔離策略有效**：
   - Qwen 在嚴格 Prompt 下可只做資訊提取，不做計算
   - 為「LLM 提取 + 規則引擎計算」組合架構打通關鍵環節

3. **發現 TravelPlus 頁面折扣標示異常**：
   - 產品頁標示「約64折」
   - 實際計算為「8.5折」（15% off）
   - 這是**真實的商業網站潛在問題**，CartRescue 的價值場景

### ⚠️ 問題與限制

1. **規則引擎對「折扣術語」解析仍有局限**：
   - 「約64折」被解析為「64% off」而非「6.4折」
   - 需要更精細的語義理解來區分「X折」與「XX% off」
   - **建議**：讓 LLM 負責「促銷類型語義分類」，規則引擎負責「數學驗證」

2. **momo 多層疊加折扣仍未完全解析**：
   - 規則引擎目前只處理「單一折扣率」
   - 「9折 + 滿額折 + 回饋點數」的組合計算仍需擴展

3. **連續 15 天無法測試雲端模型**：OpenAI / Anthropic / Gemini / Moonshot API 金鑰仍缺失。
